## 1. Resumo executivo

O estado geral do MCP está **forte**, mas não limpo. A arquitetura principal está correta: Node
`v24.15.0`, MCP `workspace-mcp/0.3.0`, `@github/copilot-sdk` `^0.3.0`, `@modelcontextprotocol/sdk`

issuer/resource/audience alinhados, e score de autonomia `96/A`.

A situação operacional está **degraded**, não por falha crítica, mas por sinais de frescor e
consistência: o último smoke Cloudflare do conector permanente está velho, com **730 minutos**, não
há `mcp_smoke_workspace` in-process registrado, e o workspace está dirty. O fallback `trycloudflare`
salvo está morto/stale há cerca de **1512 minutos**; ele está corretamente ignorado para readiness,
mas ainda é uma armadilha se alguma documentação, UI ou conector antigo apontar para essa URL.

A hipótese mais forte para “conexão perdida” ou “conexão interrompida” na UI do ChatGPT continua
sendo **interrupção no stream host/browser do ChatGPT durante chamadas longas ou payloads grandes**,
especialmente validações/logs/diffs. A evidência central é que os jobs de validação terminaram com
sucesso no servidor, enquanto a UI pode parecer interrompida. O MCP server, o OAuth e o túnel
permanente não mostram erro crítico.

Há um avanço importante em relação aos relatórios anteriores: `mcp_validation_dashboard` e
`job_get_summary` agora existem e funcionam com argumentos `{}`/shape estrito. Isso reduz bastante o
risco de stream quebrado por logs grandes. Ainda assim, há drift de metadados: `mcp_tools_status`
conta **73 tools**, mas `mcp_capabilities_summary` anuncia **71** e não categoriza as duas novas
(`mcp_validation_dashboard`, `job_get_summary`). Esse drift precisa ser corrigido antes de
considerar a tool surface coerente.

## 3. Diagnóstico da “conexão perdida” na UI do ChatGPT

### 3.1 Hipótese dominante

A mensagem “conexão perdida/interrompida” na UI parece mais compatível com **quebra do stream da
interface ChatGPT/host orchestration** do que com falha do MCP server. Ela tende a aparecer em
operações longas, especialmente quando há:

- validação com job longo;
- polling;
- leitura de logs;
- retornos com muitos campos/linhas;
- diffs textuais grandes;
- múltiplas tool calls em sequência.

### 3.2 Evidências a favor

- Túnel permanente válido.
- OAuth ready e `reauthRisk: low`.
- `critical: []` no runtime health.
- Jobs de validação concluíram com sucesso no servidor.
- Ferramentas curtas (`repo_status`, `mcp_tunnel_status`, `mcp_auth_profile`, `mcp_tools_status`,
  `mcp_validation_dashboard`, `job_get_summary`) responderam normalmente.
- As mudanças recentes justamente suprimem diffs por default e adicionam resumos compactos.

### 3.3 Camadas possíveis

| Camada                     |             Probabilidade | Evidência                                      | Ação                                  |
| -------------------------- | ------------------------: | ---------------------------------------------- | ------------------------------------- |
| ChatGPT web/browser stream |                      Alta | UI interrompe enquanto backend conclui job     | reduzir payloads, usar summaries      |
| Host MCP orchestration     |                      Alta | chamadas longas/logs são mais sensíveis        | evitar logs grandes, job async        |
| MCP HTTP server            |               Média-baixa | sem critical; mas pode retornar payload grande | output budget e timeouts              |
| Cloudflare permanente      |               Baixa-média | tunnel ok, mas smoke stale                     | refresh de smoke                      |
| OAuth                      |                     Baixa | issuer/audience/resource ok                    | persistir refresh tokens no futuro    |
| Fallback trycloudflare     | Média se usado por engano | state morto/stale                              | remover/expirar URL antiga de docs/UI |

### 3.4 Conclusão prática

O caminho correto é tratar “conexão perdida” como sintoma de **robustez de streaming e payload**,
não como prova inicial de OAuth quebrado. A mitigação imediata é:

1. usar `mcp_validation_dashboard`;
2. usar `job_get_summary`;
3. evitar `job_get_output`, exceto tail pequeno em falha;
4. manter `includeDiffPreview=false`;
5. refrescar smoke Cloudflare para remover incerteza operacional;
6. garantir que o conector ChatGPT esteja na URL permanente, não na URL `trycloudflare` antiga.

## 4. Bugs, gaps e inconsistências atuais

### P1 — Runtime health degradado por smoke stale

**Evidência:** smoke Cloudflare com 730 minutos; staleAfter 60 minutos. **Impacto:** ruído
operacional e incerteza ao diagnosticar perda de conexão. **Correção recomendada:** criar ou expor
tool curta `mcp_connector_smoke_refresh`, bounded/safe, com output compacto, que atualize
`connector-smoke.json` sem rodar suíte de testes.

### P1 — Fallback `trycloudflare` morto ainda aparece no estado

**Evidência:** processo morto, stale, idade 1512 minutos. **Impacto:** se alguém usar essa URL por
engano no ChatGPT, o resultado será conexão perdida/indisponibilidade. **Correção recomendada:**
separar estado permanente/fallback com aviso mais forte; talvez ocultar fallback morto do perfil
padrão e expor apenas sob `includeFallback=true`.

### P1 — Drift entre registry real e `mcp_capabilities_summary`

**Evidência:** `mcp_tools_status.totalTools = 73`;
`mcp_capabilities_summary.advertisedToolCount = 71`. **Tools ausentes no capabilities estático:**
`mcp_validation_dashboard`, `job_get_summary`. **Impacto:** o modelo recebe instruções para usar
tools que o summary não anuncia; score/metadados ficam inconsistentes. **Correção recomendada:**
atualizar `VALIDATION_TOOLS` em `src/copilot/mcp/tools/meta.js`, bump `CAPABILITIES_VERSION`, e
adicionar teste que compare `getAdvertisedMcpToolNames()` contra registry real.

### P1 — `mcp_tools_status` ainda lista `job_cancel` como remember candidate no nível top-level

**Evidência:** `approvalFrictionProfile` já filtra `job_cancel`, mas `rememberApprovalCandidates`
top-level ainda inclui `job_cancel`. **Impacto:** orientação contraditória para approvals.
**Correção recomendada:** reutilizar a mesma função de classificação manual/destrutiva para todos os
campos, não apenas para `approvalFrictionProfile`.

### P1 — Guidelines ainda contêm fluxo antigo com `job_get_output`

**Evidência:** `connection/profile.js` ainda possui smoke prompts como “rode validator e depois leia
output com `job_get_output`”. **Impacto:** o próprio perfil induz o padrão que causa stream
interruption. **Correção recomendada:** trocar por
`mcp_validation_dashboard -> job_get_summary -> job_get_output tailBytes<=8000 somente em falha`.

### P1 — Workspace dirty com alterações relevantes não consolidadas

**Evidência:** múltiplos arquivos MCP modificados e docs não rastreados. **Impacto:** validações
históricas podem não representar exatamente o estado atual; rollout/restart fica ambíguo. **Correção
recomendada:** antes de qualquer patch novo, estabilizar em um commit/checkpoint ou ao menos gerar
um diff review formal por arquivo.

### P2 — `repo_search_text` não aceita alias `query`

**Evidência:** chamada com `{query: ...}` falhou; schema requer `pattern`. **Impacto:** aumenta erro
de tool-call por inferência natural do modelo. **Correção recomendada:** aceitar alias `query` como
compatibilidade, ou melhorar descrição da tool no profile/golden prompts.

### P2 — Tools de input vazio são sensíveis a argumentos extras

**Evidência:** `mcp_validation_dashboard` funciona com `{}`, mas chamada com extras foi
bloqueada/recusada pela camada de tool. **Impacto:** modelos podem passar
`includeHistory`/`includeValidators` por intuição e falhar. **Correção recomendada:** aceitar opções
opcionais benignas, ou usar schema com `includeHistory?: boolean`/`includeValidators?: boolean`
ignoradas/controladas.

### P2 — HTTP MCP adapter não impõe orçamento explícito de resposta por tool

**Evidência:** mitigação de payload foi implementada em algumas tools, mas não existe camada comum
de budget no adapter/registry. **Impacto:** uma tool nova pode voltar a retornar payload gigante e
reabrir “conexão perdida”. **Correção recomendada:** adicionar guard comum de
`structuredContent`/text budget por tool, com truncamento e `outputTruncated`.

### P2 — SSE client interno reseta backoff cedo demais

**Arquivo:** `src/copilot/channel/sse-client.js` **Evidência:** `reconnectMs = 1_000` é resetado
assim que há resposta, sem validar `statusCode` ou `content-type`. **Impacto:** se endpoint retornar
401/404/429 rapidamente, o cliente pode reconectar em loop com backoff efetivamente baixo.
**Correção recomendada:** só resetar backoff após status 2xx e `content-type: text/event-stream`;
classificar status não-SSE com backoff preservado.

### P2 — SSE client interno não define timeout de conexão/leitura

**Arquivo:** `src/copilot/channel/sse-client.js` **Impacto:** conexões half-open podem ficar presas
dependendo do socket. **Correção recomendada:** `req.setTimeout(...)`, timeout inicial até primeiro
byte/connected, e encerramento controlado para acionar reconnect.

### P2 — SSE writer não trata backpressure

**Arquivo:** `src/copilot/infra/sse/utils.js` **Evidência:** `out.write(...)` é chamado sem checar
retorno `false`/`drain`. **Impacto:** em bursts/eventos grandes, pode aumentar memória/latência.
**Correção recomendada:** introduzir fila curta por cliente, drop policy para eventos não críticos,
métricas de backpressure e limite por payload.

### P2 — Smoke HTTP pode pular runtime tool-call quando OAuth exige bearer

**Arquivo:** `src/copilot/mcp/scripts/smoke-http.js` **Evidência:** se auth enforcement não está off
e não há bearer token, `runtimeHealth` é marcado como skipped/auth-required. **Impacto:** um smoke
pode validar `/health` e `tools/list`, mas não provar que `tools/call` autenticado funciona.
**Correção recomendada:** ter smoke OAuth real para o conector permanente ou gerar token dev
específico de smoke com escopo mínimo e TTL curto.

### P2 — `repo_apply_file_batch` é destrutivo por mistura de operações

**Evidência:** classificado como destructive junto com `repo_remove_file`. **Impacto:** batches
seguros pagam custo de prompt/risk class de operações destrutivas. **Correção recomendada:** separar
`repo_apply_safe_file_batch` de `repo_apply_destructive_file_batch`.

### P2 — Persistência OAuth dev issuer ainda parece in-memory

**Evidência:** audit informa refresh token rotation in-memory. **Impacto:** restart pode forçar
reauth apesar de TTL de 30 dias. **Correção recomendada:** persistir refresh-token hashes e DCR/CIMD
clients sanitizados, com rotação one-time e cleanup.

### P2 — Documentação acumulada e não rastreada

**Evidência:** 13 docs em `src/copilot/docs`, vários não rastreados, alguns nomes com
espaços/acentos, e artefatos soltos na raiz. **Impacto:** dificulta navegação, aumenta chance de
usar runbook obsoleto, polui status. **Correção recomendada:** consolidar docs em
`src/copilot/docs/archive/` e criar um índice canônico curto.

### P3 — `mcp_oauth_issuer_diagnostics` nextSteps ainda genérico

**Evidência:** mesmo `ready=true`, recomenda checar/setar JWKS. **Impacto:** ruído baixo. **Correção
recomendada:** se ready e JWKS ok, retornar “no issuer metadata fix required”.

### P3 — CORS permissivo quando origin ausente

**Arquivo:** `src/copilot/mcp/adapters/http.js` **Evidência:** `Access-Control-Allow-Origin` vira
`*` quando origin ausente/não específico; origin ausente é aceito. **Impacto:** provavelmente
aceitável para server-to-server, mas endureceria postura. **Correção recomendada:** documentar razão
ou expor modo strict para produção.

## 9. Veredito

O MCP está em uma fase boa, perto de “operacionalmente robusto”, mas com três classes de problemas:

1. **Readiness stale:** smoke Cloudflare velho e fallback temporário morto.
2. **Metadados/ergonomia:** capabilities atrasado, `job_cancel` parcialmente contraditório, prompts
   antigos ainda sugerindo logs.
3. **Stream-safety:** mitigação já começou, mas precisa virar política central para toda tool e todo
   fluxo longo.

A próxima intervenção deve ser pequena e cirúrgica: corrigir metadados, guidance e smoke freshness
antes de qualquer refactor mais ambicioso.
